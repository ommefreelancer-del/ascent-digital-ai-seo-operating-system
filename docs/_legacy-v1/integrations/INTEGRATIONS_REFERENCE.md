## Discrepancy flagged: `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`

`.env.example` documents these as a standard Google OAuth 2.0 Client (redirect URI `http://localhost:3000/api/auth/callback/google`) — that exact URL pattern is NextAuth's own default OAuth-provider callback convention (`/api/auth/callback/[provider]`). However, the full, directly-read `web/src/server/auth.ts` `authOptions.providers` array contains **only `CredentialsProvider`** — no `GoogleProvider` is registered in NextAuth. **This is recorded as an unresolved documentation/code discrepancy, not silently resolved:** either (a) `GOOGLE_CLIENT_ID`/`SECRET` are consumed by a separate, non-NextAuth route that happens to reuse the same URL convention coincidentally or for historical reasons, or (b) the `.env.example` comment is stale relative to the current `auth.ts`. **NOT VERIFIED IN CURRENT CODEBASE** which is true — confirm by grepping the codebase for `GOOGLE_CLIENT_ID` usage directly before telling a client that "Sign in with Google" exists as a login option. As of this pass, sign-in is confirmed to be email/password only.

## Verifying a connection's live state

`web/src/server/backend/integration-health-check.ts` is a real, confirmed (fully read) module. Its design principle: it calls each integration's own real, already-used server functions directly (never routes through Boss Agent, a specialist agent, or any LLM role-play) so a health check reports what a real call actually produced. Statuses: `PASS` (a real call succeeded), `FAIL` (a real call was attempted and returned a real error), `NOT_TESTED` (not connected/configured, or — Gmail specifically — no safe zero-argument read call exists), `PENDING` (Google Trends only, per its own documented blocked status — **NOT VERIFIED** what "blocked" refers to exactly; confirm directly). Every check is wrapped so one failing check can never take down the others, and no credential/token value is ever included in a result's `detail` text.
